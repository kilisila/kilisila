# bgm-mixer

USB マイクの音声と、YouTube Music などの再生音を混ぜて、配信アプリ（IRIAM）のマイク入力として届けるための試作。
リポジトリ直下の YouTube チャット表示アプリとは独立したプロジェクトとして扱う。

**root 化しない前提であり、利用者本人の個人利用に限る。** 配信アプリへの割り込みは同アプリの利用規約に抵触する可能性が高く、アカウント停止の危険がある。検証は捨てアカウントで行う。

---

## 1. 方式（案 B）

root なしの Android には仮想マイクを作る手段がない。そのため、配信アプリ自身のプロセス内でマイク読み取り処理を横取りし、BGM を足し込む。

```
[YouTube Music] --(AudioPlaybackCapture)--> [ミキサーアプリ] --(ローカルソケット)--+
                                                                                   |
[USB マイク] --> [IRIAM の録音処理] --(フックで BGM を加算)--> [IRIAM の配信] <--+
```

- ミキサーアプリ：再生音の取り込み、音量・ダッキング（話している間は BGM を下げる処理）、IRIAM への PCM 供給を担う
- 注入モジュール：LSPatch 系ツールで IRIAM の APK に埋め込む Xposed モジュール。録音処理の戻り値に BGM を加算する
- マイク自体は IRIAM がそのまま読む。USB マイクの選択は Android の自動切り替えに任せる

ハードウェアで解決する案 A（ループバック付きミキサー）は比較の上で却下した。既存の USB マイクを活かせず、追加費用がかかるため。

## 2. 段階と進捗

| 段階 | 内容 | 状態 |
|---|---|---|
| Phase 0 | 調査（IRIAM の実装基盤、録音経路、改ざん対策、再生音の取り込み可否、再署名後の起動可否） | 着手 |
| Phase 1 | ミキサーアプリ本体（取り込み・混合・PCM 供給） | 未着手 |
| Phase 2 | 注入モジュール（録音処理のフック） | 未着手 |
| Phase 3 | 実機調整（遅延、長時間安定性、HyperOS のバックグラウンド制限） | 未着手 |

Phase 0 の結果次第で Phase 2 の実装方針が大きく変わる。

- 録音が Java の `AudioRecord` 経由 → Java フックで済む（易しい）
- 録音がネイティブ（AAudio / OpenSL ES / Oboe、Unity の `Microphone` など）→ ネイティブフックが必要（難しい）
- PairIP などの改ざん対策がある → 再署名した時点で起動しない可能性が高い。回避の可否を先に判断する

## 3. Phase 0 の手順

### 3.0 判明している制約（重要）

IRIAM は **USB デバッグが有効だと起動時のチェックで終了する**（実機で確認済み）。アンチデバッグが入っていることを示しており、再署名を検知するアンチタンパーや root 検知も併せて持っている可能性が高い。これは案 B の成否に直結する。

影響:

- **静的解析（3.1）** は IRIAM を起動しないため、USB デバッグを有効にしたまま実施できる。影響なし。
- **実行時解析（3.2）** は「IRIAM の起動」と「adb 接続」が両立しないため、そのままでは実施できない。回避策は 3.2 に記す。
- **再署名テスト（3.4）** の重要度が上がった。ここで落ちると案 B は成立しない。**ミキサーアプリ本体を作る前に、3.4 を先に済ませる。**

推奨する順番: 3.1（静的解析） → 3.4（再署名テスト） → 3.2（実行時解析。できる範囲で）

### 3.1 静的解析

PC に Python 3.8 以降と adb が必要。端末を USB で接続し、USB デバッグを許可した状態で実行する。

```bash
cd bgm-mixer/phase0
python analyze_iriam.py static
```

IRIAM の APK を `phase0/out/apk/` に取り出し、実装基盤・音声ライブラリ・改ざん対策の手がかりを `phase0/out/report_static.txt` に出力する。APK 本体はリポジトリに含めない（`.gitignore` 済み）。

### 3.2 実行時の録音経路

IRIAM を起動し、配信前の準備画面などでマイクが動作している状態にしてから実行する。USB マイクを接続した状態でも一度実行する。

```bash
python analyze_iriam.py runtime
```

録音元の種別（`MIC` / `VOICE_COMMUNICATION` など）、入力デバイス、サンプリング周波数、適用中の音声エフェクト（エコーキャンセラーなど）を `phase0/out/report_runtime.txt` に出力する。

ただし IRIAM は USB デバッグ有効時に起動しない（3.0）ため、USB 接続の adb とは両立しない。次の順で回避を試す。

1. **ワイヤレスデバッグを試す。** 開発者向けオプションの「ワイヤレスデバッグ」は「USB デバッグ」とは別のトグル。これだけを有効にし、USB デバッグは無効のまま `adb pair` / `adb connect` で接続して IRIAM が起動するか確認する。IRIAM が USB デバッグのトグルだけを見ているなら、この方法で実行時解析ができる。
2. **両方弾かれる場合**（IRIAM が adb の有効状態そのものを検知している場合）、root なしでは実行時の dumpsys を取得できない。この場合は実行時解析を諦め、静的解析（3.1）と再署名テスト（3.4）の結果だけで Phase 1・Phase 2 の方針を決める。録音がどの層か（Java か、Agora 等のネイティブか）は静的解析でおおむね判別できる。

`report_*.txt` の内容を共有すれば次の判断に進める。`raw_*.txt` には他のアプリの情報が含まれるため共有しない。

### 3.3 再生音の取り込み可否（Phase 1 の最小版で確認）

YouTube Music が AudioPlaybackCapture を拒否していないかを実機で確認する。最小の検証アプリを用意してから実施する。

### 3.4 再署名した IRIAM の起動確認（手作業）

1. LSPatch 系ツール（JingMatrix/LSPatch、NPatch など）の最新版を入手する
2. IRIAM の APK を、モジュールなしでパッチする
3. 元の IRIAM をアンインストールしてから、パッチ済みのものをインストールする（署名が異なるため上書きできない。アプリ内データは消える）
4. 捨てアカウントでログインし、配信の準備画面まで進めるかを確認する

起動直後に終了する、ログインできない、警告が出るなどの場合は、改ざん検知が働いている。その時点で案 B の継続可否を判断する。

## 4. 未検証事項

特に次の点が方式の成否を決める。

- 再署名した IRIAM が起動・ログイン・配信できるか（**最重要**。IRIAM はアンチデバッグを持つことが判明済みで、アンチタンパーも持つ可能性が高い。ここで落ちると案 B は成立しない）
- IRIAM の録音処理がどの層で行われているか（Java の `AudioRecord` か、Agora 等のネイティブか）
- YouTube Music の再生音を AudioPlaybackCapture で取り込めるか

判明済み:

- IRIAM は USB デバッグ有効時に起動しない（アンチデバッグあり）
